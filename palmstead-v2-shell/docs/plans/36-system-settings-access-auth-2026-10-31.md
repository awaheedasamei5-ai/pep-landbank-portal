## Design principles

1. **Separate identity, contact and authorization.** `auth.users` owns login factors (verified email, verified phone, OAuth identities). `profiles` owns the display name, contact phone, staff bio and employment assignment. A verified login phone may populate the contact phone after successful verification; entering a contact number never silently makes it a login factor. Authorization derives from server-owned tables, not `raw_user_meta_data` or local storage.
2. **Management controls employment and access.** Staff can edit safe self-service fields (preferred display/contact details, address, avatar, personal settings) but cannot assign role, department, employment status, user email, permissions or approval authority. High-impact changes are audited.
3. **Deny by default for sensitive actions.** An app grant is not merely a sidebar filter. It must gate routes, data reads, RPCs, mutations, exports and background jobs. Existing RLS must be inventoried before each app is placed behind grants. Avoid turning on a grant that UI honours but database ignores.
4. **Preserve historical company data.** A newly invited staff member with a system-wide grant can read all records allowed by that grant regardless of joining date. Personal records remain tied to owner/user/agent key and do not inherit colleagues' history. Grant changes must not rewrite ownership or timestamps.
5. **Step-up for finance and administration.** Staff-management, access grants, Finance approval and bank actions require a current active manager or designated grant, with audit. Phone SMS is a convenient login factor, not a replacement for stronger MFA on high-impact actions.

## App scope and access catalogue

Catalogue keys follow `sidebar-items.ts` and are persisted as stable IDs. The matrix is a review target, not permission already implemented.

| Class | Apps | Default data scope |
|---|---|---|
| Company records | Master Pipeline, Client Database, Plot Inventory, Allocations, Company Leads, Directory, Announcements, Memorandum, Accounting, Contract of Sale, Quotation, Staff Hub | Existing permitted company history; sensitive views and writes by explicit feature grants |
| Mixed company/personal | Operations Tracker, Site Visits, Enquiries, Referrals, Complaints, Attendance, Leave, Banner Tracking, Site Visit Authorization, Chat, Document Vault, Analytics, Smart Insights, Data Check, Leaderboard | Company/team records by role and app feature; personal entries by owner; confidential subrecords separately checked |
| Personal | Notes, My Portfolio, personal notifications and personal Staff Report | Start empty for each new staff account; owner-only except audited management workflows |
| Platform administration | Team Roster, System Health, System Settings | Management only, with stricter feature checks for access and identity changes |

Each app has a feature vocabulary: `view`, `create`, `edit_own`, `edit_team`, `delete_own`, `delete_team`, `approve`, `export`, `settings`, and app-specific actions (for example `finance.pay`, `finance.reverse`, `operations.assign`, `leave.reschedule`). A **full** grant includes the defined non-admin feature set for that app; **restricted** means read-only/company-visible; **limited** stores an explicit subset; **none** denies entry. Sensitive `settings`, `approve`, `pay`, `reverse`, role and access administration are never silently included in a generic full grant. Feature names and consequences appear in plain language in Management UI.

Grant precedence: explicit user deny > explicit user allow > department template > role template > safe baseline. Active Management retains emergency administration but cannot remove the final active access administrator. Suspended profiles deny all. Every effective-access result includes source and version for UI explanation. A manager can preview a staff member's effective access without impersonating them. All grant changes write actor, subject, app, old/new state, reason and timestamp to an immutable audit table. Approval role assignments already present in Finance remain separate business permissions and must be reconciled with app entry grants rather than replaced.

## Data model and security rollout

Phase 1: tighten `protect_profile_authorization_fields` so self-service changes cannot alter `department`, `position`, `email`, `name` (if it is a legal/payroll identity), `id_number`, employment fields or permission-related data. Keep Management updates and server provisioning. Add profile self-service form using an explicit allowlist; no `select('*')` update. Build Staff Settings for biodata, contact preferences, verified login factors and session controls. Management Settings displays staff directory, onboarding status, profile corrections and access entry point. Run role-switched database tests for owner, colleague, manager and disabled user.

Phase 2: create `app_catalogue`, versioned role/department templates, per-user overrides and append-only `access_audit`. RLS: staff read their effective grants; Management reads and changes grants through validated RPC only; no direct grant table writes from browsers. The server computes effective access with owner and department rules and explicit deny priority. Add route and sidebar gates plus app-specific RLS/RPC gates in small slices. Begin with Settings/Team Roster, then company data, then finance and personal apps. Audit every existing policy, definer function, export and Edge Function before switching each app. Backfill role templates to reproduce current valid staff access so deployment does not unexpectedly hide existing work.

Phase 3: invitation-only onboarding. Management invites email and role/department; use the existing `allowed_emails`/`handle_new_auth_user` mechanism after security review. Public registration routes redirect to a single invite acceptance flow and never display passwords. New accounts become active only after invitation and verification. The login UI offers password, Google (only after provider verified and invited-user linking confirmed), and phone OTP (only to already verified phone attached to an existing invited account). Never auto-create a user from a phone OTP. A new staff member receives company-wide historical data according to the grant, while personal apps remain empty.

Phase 4: phone verification and Arkesel OTP. Phone change begins from an authenticated session, verifies a challenge sent to the new number and then updates the verified Auth phone and contact data. Supabase Auth generates/verifies OTP; its Send SMS Hook delivers through Arkesel with server-held key, signature validation, timeout, retries and idempotency. Never build a second OTP store or log tokens. Configure provider/hook and project rate limits in V2 only. Use E.164 phone normalization, Ghana default only after explicit UI country selection, masked display and no OTP disclosure in logs. Block OTP sign-in until hook/provider and staff account linking are proven in a non-live test and one controlled live test. When enabled, `signInWithOtp` uses `shouldCreateUser:false`; `verifyOtp` establishes the session, then the same active-profile gate runs as password login.

Phase 5: recovery and security. Email reset uses Supabase's token flow, generic response, correct production redirect allowlist and a new-password form. Password change from Settings requires current password where supported. Sign-out everywhere and sessions view are tested. Login and recovery errors do not reveal whether an account exists. Use Supabase project limits for password, OTP send/verify and SMS budget, plus CAPTCHA/edge throttling where needed. Audit suspicious sign-in and access changes without recording secrets. High-impact flows should add TOTP/passkey step-up where provider support and staff enrollment allow it; SMS alone has SIM-swap risk.

## Settings information architecture

Staff Settings: Profile (name, role, department, verified contact status, editable bio), Notifications (SMS and in-app delivery preferences by reminder class, mandatory work notices distinguished from optional), Security (password, Google identity status, verified phone, active sessions), Appearance (existing shell theme controls), and My Access (effective app grants, read-only, clear request path). Forms are short sections and work at 320 px. Save state, validation, errors and audit hints must be visible. A new phone is pending until verified; changing a contact number does not silently redirect financial or leave SMS.

Management Settings: Team (invite, active status, employment fields, last activity), Access (staff/department/role views, app permission matrix, effective access preview, audit), Communication (Arkesel delivery health and templates without exposing secret keys), Security (provider status, rate limit and recovery health), and System (integration status and data boundaries). App-specific business settings stay inside their app, as the repo convention requires. Management UI never displays secret keys, OTPs, password hashes or full sensitive identity numbers. Critical changes have confirmation and a reason.

## SMS consumer contract

Every reminder job resolves a recipient through a central contact resolver at send time: active profile, verified/allowed phone, opt-in and message category, normalized E.164 number. Do not cache a phone on old leave/finance/operations rows. Record delivery result, template and source event but never OTP content. Business workflows are idempotent and retry bounded. Migrating existing jobs is an app-by-app pass: Leave, Operations, Accounting, allocation, announcements. Staff settings must say which alerts are mandatory and which are optional; the UI should not promise device alarms when the app is closed unless a push subscription or SMS fallback is actually active.

## Verification and release gates

For every slice: inspect V2 schema and policy, write source migration, test with rollback transaction as Management, staff owner, colleague and inactive user; run typecheck/build and relevant unit tests; inspect mobile/light/dark UI; verify Management and Staff live against exact preview; then read `DEPLOY_INSTRUCTIONS.md` and release to `rebuild`/V2 only. No real customer/staff SMS in automated tests. A controlled live SMS test uses one consenting test account and confirms Arkesel result without exposing OTP. Test a new staff invite against historical company data and empty personal data. Test direct URL, RPC and Data API bypass attempts, not only hidden menu items. Document any remaining app permission migration plainly.
